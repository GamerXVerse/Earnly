# Screen Time feasibility

Reviewed November 21, 2026 against Apple's public documentation and the iPhoneOS 26.5 Swift interfaces installed with Xcode 26.6. The simulator compiled the authorization adapter with the package's iOS 17 minimum. Entitled behavior and repeated allowance cycles require signed physical-device experiments.

## Authorization and selection

For student-managed restrictions, request `AuthorizationCenter.shared.requestAuthorization(for: .individual)` after explaining which selections Earnly will shield and how to revoke access. Apple authorizes the device owner on their own device. The original `.child` mode requires approval from a parent or guardian in the Family Sharing group and has additional protections. Individual mode does not impose the parental mode's restrictions on app deletion and iCloud sign-out. Product copy should describe Earnly's individual restrictions as voluntary. [AuthorizationCenter](https://developer.apple.com/documentation/familycontrols/authorizationcenter) · [WWDC22 Screen Time API](https://developer.apple.com/videos/play/wwdc2022/110336/)

Present the system `FamilyActivityPicker`. Its confirmed `FamilyActivitySelection` includes opaque app, activity-category and web-domain tokens. Store the selection only in the Apple adapter and pass the tokens to Device Activity and Managed Settings. Reject an empty selection before registering events, because an event with all three token sets empty covers all activity. Apple's documentation says revocation invalidates existing tokens. Refresh status at launch and foreground entry, discard revoked selections, and require a fresh picker session before resuming. The newer data-access authorization exposes identifiers beyond Earnly's needs. Phase 2 uses the standard Family Controls capability and opaque tokens only. [FamilyActivityPicker](https://developer.apple.com/documentation/familycontrols/familyactivitypicker) · [FamilyActivitySelection](https://developer.apple.com/documentation/familycontrols/familyactivityselection) · [DeviceActivityEvent initializer](https://developer.apple.com/documentation/deviceactivity/deviceactivityevent/init(applications:categories:webdomains:threshold:)) · [Data-access status](https://developer.apple.com/documentation/familycontrols/authorizationstatus/approvedwithdataaccess)

## Scheduling and thresholds

- `DeviceActivityCenter.startMonitoring(_:during:events:)` registers a calendar-based `DeviceActivitySchedule` and named thresholds. `DeviceActivityMonitor` receives matching event and interval callbacks in its extension, including when the host is absent. Frontmost usage of the specified apps, categories and web domains accumulates within the interval. Some app and domain associations are implicit. Safari contributes domain usage, as do third-party browsers that use Apple's Screen Time webpage API. [Schedule](https://developer.apple.com/documentation/deviceactivity/deviceactivityschedule) · [Event](https://developer.apple.com/documentation/deviceactivity/deviceactivityevent) · [Monitor](https://developer.apple.com/documentation/deviceactivity/deviceactivitymonitor)
- The minimum monitoring interval is **15 minutes**. A broad calendar interval can contain a **10-minute usage threshold**. The interval governs eligibility for monitoring, while threshold minutes measure activity. Interval boundaries are calendar-based and Apple's documentation describes particular callback behavior when device use resumes or monitoring stops. A 10-minute elapsed-time schedule is outside the documented constraint. [Minimum interval](https://developer.apple.com/documentation/deviceactivity/deviceactivitycenter/monitoringerror/intervaltooshort) · [Interval end](https://developer.apple.com/documentation/deviceactivity/deviceactivitymonitor/intervaldidend(for:))
- Re-registering the same activity name overwrites its schedule and events. Apple says callbacks can start as part of registration if the interval is already active. Stopping a registration may trigger its interval-end callback. Restrict registrations to the minimum needed, persist the intended generation before calling the API, and filter callbacks using the activity and event names. Apple documents errors for excessively many or tightly scheduled activities. [Start monitoring](https://developer.apple.com/documentation/deviceactivity/deviceactivitycenter/startmonitoring(_:during:events:)) · [Stop monitoring](https://developer.apple.com/documentation/deviceactivity/deviceactivitycenter/stopmonitoring(_:))
- The installed SDK makes `includesPastActivity` available from iOS 17.4. For a fresh allowance, test with `false`. With `true`, activity before registration can count within the schedule, including activity back to a rounded hour for a non-round start. On iOS 17.0–17.3 use the earlier initializer. Apple documents counting from monitoring start when that initializer's schedule is already active. Neither documented detail guarantees behavior across rapid re-registration, reboot, schedule rollover, or repeated rewards. [Past activity](https://developer.apple.com/documentation/deviceactivity/deviceactivityevent/includespastactivity) · [Earlier initializer](https://developer.apple.com/documentation/deviceactivity/deviceactivityevent/init(applications:categories:webdomains:threshold:))
- A callback establishes threshold evidence for one generation. Keep dashboard remaining minutes unavailable. Do not assume real-time delivery, exactly-once delivery, continuous app-usage updates, precise overshoot, or that a threshold by itself can rearm. The optional `DeviceActivityReport` extension can render a privacy-preserving report in its sandbox. Its usage results are unsuitable as a host-callable usage meter or ledger source. [Threshold callback](https://developer.apple.com/documentation/deviceactivity/deviceactivitymonitor/eventdidreachthreshold(_:activity:)) · [Report isolation](https://developer.apple.com/documentation/deviceactivity/deviceactivityreport)

## Shield and return to Earnly

Use one dedicated named `ManagedSettingsStore` shared by the host and monitor extension. Apply selected app and domain tokens through `shield.applications` and `shield.webDomains`. Apply category tokens with the appropriate application and web domain category policies. Clear only Earnly's named store settings to release its shield. Store confirmation describes Earnly's own settings. Other stores or system policies can still restrict access. Verify that a broad category cannot prevent students from returning to Earnly, and test any supported exclusion for the selected category policies. [ManagedSettingsStore](https://developer.apple.com/documentation/managedsettings/managedsettingsstore) · [Shield settings](https://developer.apple.com/documentation/managedsettings/shieldsettings) · [Named stores](https://developer.apple.com/videos/play/wwdc2022/110336/)

A **Shield Configuration** extension supplies the system shield's labels, icon, colors and buttons. Students complete practice inside Earnly. A **Shield Action** extension responds to supported button actions. On the iOS 17 baseline, the supported responses are `.none`, `.close` and `.defer`. Use `.close` and shield instructions to have the student open Earnly from the Home Screen or App Switcher. The installed SDK exposes `.openParentalControlsApp` from **iOS 26.5**, which instructs the system to open the app responsible for that shield. Test the response on devices in individual mode before promising a one-tap return. Use an availability check and keep the manual journey for earlier releases. [Managed Settings UI](https://developer.apple.com/documentation/managedsettingsui) · [Shield responses](https://developer.apple.com/documentation/managedsettings/shieldactionresponse) · [Open parental controls app](https://developer.apple.com/documentation/managedsettings/shieldactionresponse/openparentalcontrolsapp)

## Signing and target plan

1. In the Earnly application project, use the team's registered application ID and development signing to add the Family Controls capability (`com.apple.developer.family-controls`). Add and sign a **Device Activity Monitor** extension to handle threshold delivery and shielding when Earnly is absent. Add **Shield Configuration** and **Shield Action** targets when implementing custom instructions and return actions. Add **Device Activity Report** only if a separate usage report becomes a product requirement.
2. Configure each Screen Time extension with the same team's signing and its real registered identifier and Family Controls capability. The Apple Developer Account Holder must request distribution approval for the app and **each** included Screen Time extension. Confirm the Assigned status and intended distribution methods in Certificates, Identifiers & Profiles, then regenerate or refresh the relevant provisioning profiles. Development capability and a successful simulator build establish neither distribution approval nor TestFlight readiness. Inspect signed entitlements on the archived host and each extension before distribution. [Family Controls entitlement requests](https://developer.apple.com/documentation/familycontrols/requesting-the-family-controls-entitlement)
3. Register a real App Group and add membership to the host and only extensions that need shared data. Resolve its container through `FileManager.containerURL(forSecurityApplicationGroupIdentifier:)` and handle missing access as a configuration fault. Phase 1 adds no target, entitlement or signing values. [Configuring App Groups](https://developer.apple.com/documentation/xcode/configuring-app-groups)

## Shared state and repeated allowance experiment

Keep the learning history and reward ledger in the host container with one writer. The App Group should contain only the opaque token payload, selection revision, current generation, intended shield state and small threshold receipts. Keep unrelated learning records and preferences outside the App Group. Use a transactional SQLite store with schema versioning, bounded lock waits, and unique generation keys. A thin repository can use native SQLite. Separate the threshold inbox from the host ledger. An atomic file replacement protects a snapshot from partial writes but cannot serialize two processes doing read-modify-write. Shared defaults can hold independent preferences and should stay outside the accounting transaction.

1. Prototype one active registration in a broad calendar window with one event per generation. Persist the intended threshold, generated activity/event ID, and selection revision before registration. During a reward, keep the shield applied until registration succeeds. Verify the generation at each effect, clean up the retired registration, release only that store's shield, and confirm activation in the host ledger. Check the existing registration by name when repeating a partially completed install. A retry must preserve the original credit and avoid restarting an already installed event unnecessarily.
2. In the monitor extension, transactionally fence the callback against the published generation and upsert a unique receipt. Serialize shield effects across host and extension using the same generation and a documented locking or ownership policy. The receipt should track whether shielding was confirmed so a crash between receipt commit and shield application is recoverable. The extension applies the named store shield without waiting for Earnly to foreground. The host reconciles the desired and actual store state on launch, consumes receipts through `SharedThresholdInbox`, and acknowledges only after the local commit. Repeat reads, duplicate callbacks and late acknowledgments must be safe. Treat missing group state, an unknown schema and an early threshold as reconciliation faults. Preserve bytes and credits while recovering. Never interpret an unknown generation as a new reward.
3. Run signed device trials on iOS 17.0–17.3 where available, iOS 17.4 or later, and current iOS. Use category, single-app and web selections. For both initial allowances, measure under- and over-counting through multiple consecutive grants with known prior usage. Compare replacement and stop/re-register under active intervals and check whether a completed or delayed threshold repeats. Test the effect of immediate callbacks during installation, crashing after each durable/OS step, the app terminated while a threshold fires, rapid retries, reboot before and after first unlock, authorization revocation, selection changes, time-zone changes, DST, and interval rollover while a reward is partly used. Verify both shield return paths and ensure the category policy keeps Earnly accessible.
4. Approve the repeated cycle only if trials show reliable new usage accounting and recoverable transitions across supported versions. If replacement fails that test, trial one fixed daily schedule with a single threshold and an explicitly documented interval-bound unlock policy. That changes the product promise and requires product approval. Preserve earned credits during unresolved monitoring failures and keep exact remaining usage unavailable.

## Privacy and review

Keep tokens and all associated use evidence local and out of logs. Limit retained data to selection, operational receipts, policy and learning/reward records. Explain the purpose and revocation path before authorization. Provide a local reset path that clears Earnly's applied settings, tokens and monitoring registrations in the correct order. Establish the retention and backup policy before shipping. Keep collection and sharing declarations aligned with the actual binary. Apple's App Privacy guidance treats on-device-only processing differently from server collection. App Review guidelines 1.3 and 5.1.4 have separate requirements for children and Kids Category apps. Review age rating, category, privacy policy and applicable children’s privacy obligations with the release owner. Apple capability approval and App Review are separate. [App privacy details](https://developer.apple.com/app-store/app-privacy-details/) · [App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/) · [Kids design and review](https://developer.apple.com/kids/)

## Phase 2 implementation update

The native path implements the generation-specific design. It registers a 24-hour nonrepeating calendar window anchored two minutes before preparation, with one exact generation-named event and `includesPastActivity: false`. It compares the registered interval and event with the intended configuration. The window's duration and the usage threshold remain independent. The host and extension check generation identity, and a window expiration or disappeared registration becomes an interruption rather than resetting already accrued usage. Frequent short windows would pressure registration limits and encounter the 15-minute floor. Cumulative threshold progression would require reliable prior-usage and overlap semantics, especially across restarts and rollover. Those limitations motivate the generation strategy, whose real fresh accounting remains a signed-device acceptance test. iOS 17.0–17.3 can use the development simulation; the native engine requires iOS 17.4 for explicit previous-activity exclusion. [Device Activity event initializer](https://developer.apple.com/documentation/deviceactivity/deviceactivityevent/init(applications:categories:webdomains:threshold:includespastactivity:)) · [Monitoring registration](https://developer.apple.com/documentation/deviceactivity/deviceactivitycenter/startmonitoring(_:during:events:))

The native selection guard accepts explicit web domains. It handles explicit app tokens only when the public Managed Settings application model resolves Earnly's own token, which is removed before persistence and checked again before shielding. Availability of the host token in both processes must be verified on physical devices. If it is absent, the app selection is rejected. Category shielding supports an exception token in Managed Settings, but Device Activity exposes no equivalent per-app exception for a category's cumulative event. Phase 2 therefore rejects broad categories. Mixed app and web selections can reflect implicit app-domain associations. Combined accounting and browser support require device measurements. [Application model](https://developer.apple.com/documentation/managedsettings/application) · [Category shielding](https://developer.apple.com/documentation/managedsettings/shieldsettings/activitycategorypolicy) · [Combined event semantics](https://developer.apple.com/documentation/deviceactivity/deviceactivityevent)

The monitor owns a local App Group journal and shields from the extension callback. The shield action uses the documented `.openParentalControlsApp` response only on iOS 26.5+ and only when explicitly enabled in both shield targets for validation. Apple describes opening the controlling app but does not specify individual-mode results in that response reference. The default uses `.close` and manual return. The [device acceptance plan](device-test-plan.md) contains the rollout gates and the fallback tests. [Shield action response](https://developer.apple.com/documentation/managedsettings/shieldactionresponse/openparentalcontrolsapp)
